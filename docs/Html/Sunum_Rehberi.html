🎤 Sunumda Ne Anlatabilirim?

  • Müşteri QR kodu tarayınca CSPRNG ile 256 bitlik güvenli bir token üretiliyor, SHA256 ile hash'lenip veritabanına kaydediliyor. CSPRNG = Kriptografik güvenli rastgele sayı üretici. Normal random'dan farkı: tahmin edilemez. SHA256 = Tek yönlü hash fonksiyonu: token'ı hash'e çevirebilirsin ama hash'ten token'ı bulamazsın.
  • Token HttpOnly + Secure + SameSite cookie olarak tarayıcıya yazılıyor. HttpOnly = JavaScript erişemez (XSS koruması). Secure = Sadece HTTPS üzerinden gönderilir. SameSite = Başka sitelerden gelen isteklerde cookie gönderilmez (CSRF koruması).
  • Sliding Expiration: Her istekte süre 90 dakika uzar. Müşteri aktif olduğu sürece oturumu kapanmaz. Örn: Saat 12:00'da QR taradın, 12:30'da menüye baktın → süre 14:00'a uzar. Ama hiç işlem yapmazsan 13:30'da oturum kapanır.
  • Replay Attack koruması: Token bir kez kullanılınca "Kullanıldı" olarak işaretleniyor. Birisi eski QR linki kopyalayıp tekrar açarsa, token zaten kullanılmış olduğu için reddedilir.
  • Middleware yazdım: Her gelen istekte cookie'den token'ı okuyup veritabanından doğruluyor. Middleware = İstek ile Controller arasında çalışan kontrol mekanizması. Bir nöbetçi gibi düşün — kimliği geçersizse içeri almıyor.
  • Rate Limiting ekledim: Dakikada 10 istek sınırı + Garson çağır butonu 5 dakikada 3 kez sınırlı. Kötü niyetli kullanıcının sunucuyu istek yağmuruna tutmasını engeller. Belirli sürede kaç istek yapılabileceğini sınırlıyor.
  • Ekstra: Admin layout (sidebar), Masa yönetimi (CRUD + QR kod üretimi) ve Müşteri menü sayfası UI'ını da bu hafta başlattım. Plandan öne çekme! Admin paneli ve menü sayfası aslında 6-7. hafta konusuydu ama erken başladım.

Müşteri QR Tarar → /qr/{masaNo} ↓ Token Üret: RandomNumberGenerator → 256-bit hex string ↓ Hash'le: SHA256(Token) → Oturum tablosuna kaydet ↓ Cookie Yaz: HttpOnly + Secure + SameSite=Strict ↓ Middleware: Her istekte → cookie oku → hash'le → DB'den doğrula ↓ Geçerli? → SonIslemTarihi güncelle (sliding) Geçersiz? → 401 Unauthorized

🎤 Sunumda Ne Anlatabilirim?

  • Sepet verisi PostgreSQL'de saklanıyor, Redis gibi geçici bellekte değil. Tarayıcı kapansa bile sepet kaybolmuyor. Redis = Bellekte çalışan geçici veri deposu, hızlı ama kaybolabilir. Biz DB kullandık → müşteri sayfayı yenilese bile sepeti durur.
  • Seçilen opsiyonlar (Büyük Boy, Tam Yağlı Süt gibi) JSON formatında veritabanında saklanıyor. Her sepet detayında SeciliOpsiyonlar sütununda şöyle bir yapı var: [{"Ad":"Büyük Boy","EkFiyat":20.00}]. PostgreSQL'in jsonb tipi bunu hızlıca sorgulatır.
  • Latency optimizasyonu yaptım: Supabase sunucusu Stockholm'de, biz Türkiye'deyiz. 4 ayrı DB çağrısı yerine tek seferde hesaplayıp tek SaveChanges çağırısı yaptım. Her DB çağrısı ~100-200ms ping sürüyor. 4 çağrı = 800ms. Tek çağrı = 200ms. 4 kat hız kazanımı!
  • Sepet işlemleri AJAX ile çalışıyor — sayfa yenilenmeden ürün ekleniyor, adet değişiyor. AJAX = Sayfayı yenilemeden arka planda sunucuyla iletişim kurma. fetch() API ile JSON veri gönderip alıyoruz.
  • Müşteri arayüzünü off-canvas tasarımla yaptım: Sepet sağdan kayarak açılıyor, sayfa değişmiyor. Off-canvas = Gizli panel. Bootstrap'ın Offcanvas bileşeni. Mobilde kullanıcı deneyimini çok artırıyor.
  • 15 unit test yazdım: ekleme, çıkarma, adet güncelleme, boş sepet, opsiyon fiyat hesaplama, pasif ürün kontrolü... Her olası senaryoyu test ediyorum. Mesela "pasif ürün eklenmeye çalışılırsa hata fırlatmalı" gibi edge case'ler.

🎤 Sunumda Ne Anlatabilirim?

  • Sipariş sistemi State Machine pattern ile çalışıyor. 9 farklı durum var ve her durumdan sadece belirli durumlara geçilebilir. State Machine = Geçerli durumları ve geçiş kurallarını tanımlayan yapı. Örn: "Hazır" durumundaki sipariş "Onaylandı"ya geri dönemez — sadece "Teslim Edildi"ye geçebilir. Geçersiz geçiş denemesi hata fırlatır.
  • Sepetten siparişe dönüşüm Transaction ile atomik çalışıyor: sipariş oluşturma + sepet temizleme ya birlikte başarılı olur ya da ikisi de geri alınır. Transaction = "Ya hep ya hiç" garantisi. Elektrik gitse bile veritabanı tutarsız kalmaz. Sepet silindi ama sipariş oluşmadı gibi bir durum imkansız.
  • RowVersion (Optimistic Locking): İki garson aynı anda aynı siparişin durumunu değiştirmeye çalışırsa sistem çakışmayı algılar. Her sipariş kaydının bir "versiyon numarası" var. Güncelleme sırasında versiyon kontrol edilir — eğer biri araya girip değiştirmiş ise "sayfa yenile" uyarısı verilir.
  • SignalR ile gerçek zamanlı bildirimler: Admin ürün değiştirince müşteri menüsü anında güncelleniyor. Yeni sipariş gelince admin paneline alarm çalıyor. SignalR = WebSocket tabanlı gerçek zamanlı iletişim kütüphanesi. Sunucu, istemciye veri "push" edebilir (istemci sormadan). 11 farklı bildirim noktam var.
  • Admin panelinde CRUD sayfaları yaptım: Kategori, Ürün, Opsiyon ekleme/düzenleme/silme + Fotoğraf upload + Sipariş durum yönetimi. CRUD = Create, Read, Update, Delete. Dört temel veritabanı işlemi. Admin tüm menü içeriğini web üzerinden yönetebilir.
  • GitHub Actions ile CI/CD pipeline: Kod push'landığında otomatik build → test → deploy çalışıyor. CI/CD = Sürekli Entegrasyon / Sürekli Dağıtım. Her commit'te otomatik: 1) Projeyi derle, 2) 59 testi çalıştır, 3) Başarılıysa sunucuya gönder.
  • Ekstra: Garson çağırma (alarm sesli), sipariş fiş görüntüleme, tekrar sipariş verme, opsiyon zorunlu/opsiyonel toggle, ürün açıklamaları ve emoji placeholder sistemi.
